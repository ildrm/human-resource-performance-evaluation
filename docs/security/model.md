# Security model and open risks

Implemented controls: random UUID object IDs; tenant-constrained queries; tenant-scoped composite foreign keys; PostgreSQL row-level policies for non-owner application users; an API startup check that rejects a connection role bypassing row security on any tenant table; scrypt password hashes; opaque database-backed HttpOnly, SameSite session cookies; eight-hour expiry and immediate logout revocation; active-user and current-role check per request; origin checks for writes; security headers; one-megabyte request bodies; PostgreSQL-backed login throttling keyed to a digest of tenant and login identity; and object-level checks for employee evaluation, evidence, goals, development actions, improvement plans, governance cases, and context records. A calculated review requires a submitter, a different calibration actor, and a different publication actor from the submitter. The employee cannot submit, calibrate, or publish their own review. An administrative review also requires a current model evidence dossier reviewed by an actor other than its author. Formal improvement plans require independent HR activation and decision, employee response, review meeting, and independent appeal resolution. Safety and compliance cases require separate triage, finding, and resolution actors; a triaged or confirmed case holds administrative publication. Submitted context and unresolved review conflicts also hold publication until independent review records a decision and any necessary replacement actor is assigned.

The web server proxies API calls on the same origin. The database app role must never own tenant tables. Migration credentials are separate. Application and migration URLs and passwords are environment values. Session tokens are random and only their SHA-256 hashes are stored in PostgreSQL. The `logout-all` endpoint revokes every current session for the user. Deploying this change invalidates earlier signed-cookie sessions and requires users to sign in again. Review discussion uses distinct shared and internal channels. The employee API and self export omit internal messages; message text is not copied into audit or outbox payloads.

Known risks before production use: no SSO or MFA, no network-wide/IP abuse control, no file uploads or malware scanning, no secret rotation, no formal penetration test, no vulnerability review, no retention/deletion or legal-hold workflow, no scheduled production backup restore drill, no external delivery worker, and no formal jurisdiction-specific privacy review. Expired session rows require a scheduled cleanup policy. The self-service copy omits unpublished reviews and anonymous feedback responses and is not a complete jurisdiction-specific data subject request process.

Login counters use a keyed HMAC of normalized tenant and email, with the database connection secret as the key. A 15-minute window locks one identity after ten failures; successful login removes its counter. All API instances share the PostgreSQL table; an hourly task removes entries older than one day. Because the public endpoint accepts arbitrary identity strings, a separate edge-level abuse limit is still needed to prevent large volumes of unique login attempts. The counter table is outside tenant RLS because the tenant may not exist before authentication; it stores no raw email or IP address.

The audit chain serializes writes through the tenant row and hashes previous hash plus event details. Database triggers reject updates and deletes to audit events, calibration decisions, goal revisions and check-ins, and development action events; improvement-plan and governance events are also append-only. `GET /v1/audit/integrity` verifies linkage, the tenant head, and stored content for events created after migration 003. Earlier events lack their original canonical payload and are reported as `PARTIAL`; their linkage can be checked but their content cannot be fully reverified. The chain is not independently anchored and is not a complete tamper-proof log. The outbox stores event references without employee details; delivery is not yet implemented.

The feedback API accepts one response per invitation and releases a summary only after a separate reviewer closes the campaign. Every anonymous relationship group with a configured weight must meet the campaign's minimum respondent threshold; otherwise the weighted summary is suppressed. Self ratings are shown only to the subject and are excluded from the weighted summary. Individual response text, respondent identities, and live totals have no read endpoint. Small populations and overlapping campaigns may still permit inference, so this is not a complete anonymity guarantee.
