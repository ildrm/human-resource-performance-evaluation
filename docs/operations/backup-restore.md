# PostgreSQL backup and restore

This is a development procedure for the Docker Compose stack. A production backup plan also needs encrypted off-host copies, access controls, monitoring, a defined retention period, object storage backup, and agreed recovery point and recovery time objectives. Those controls are not implemented here.

Create a custom-format database backup with `pg_dump -U postgres -d hpi -Fc -f /tmp/hpi.dump` inside the PostgreSQL container. Restore into a **new** database with `createdb -U postgres hpi_restore_test` followed by `pg_restore -U postgres -d hpi_restore_test /tmp/hpi.dump`. Check both database counts and representative evaluation replay before using a restored database. Remove the temporary copy after verification.

With the API container running, set `RESTORE_DATABASE_NAME` to the scratch database name and run `pnpm verify:restore` in `apps/api`. The command only accepts names beginning with `hpi_restore_`, connects through the non-owner application role, replays saved calculation inputs and evidence-quality policies, and exits nonzero on a score, status, or quality-index mismatch. Its current per-tenant limit is 10,000 evaluations; larger restores need a paginated verifier.

On 29 September 2026, a fresh synthetic local PostgreSQL 18.6 custom-format backup was restored into a temporary database after migration 014. Source and restore counts matched: **2 tenants, 27 evaluations, 806 audit events, 3 context records, 3 governance cases, 4 improvement plans, and 14 migration records**. The restore command exited successfully. The temporary database and backup file were removed. This proves only a local database restore; no production recovery time or data-loss objective has been measured.

A second custom-format backup after migration 015 restored successfully on the same date. Live and restored counts matched: **2 tenants, 31 evaluations, 968 audit events, 8 context records, 5 governance cases, 6 improvement plans, 1 binary proportion metric, and 15 migration records**. The scratch database and backup were removed. This was a schema and representative count check; application replay against the restored database and a timed production recovery drill remain open.

A final synthetic backup after migration 016 restored successfully. Source and restore matched at **2 tenants, 35 evaluations, 1,151 audit events, 5 organization units, 4 employee assignments, 4 binary proportion metrics, and 16 migrations**. The non-owner application role replayed **all 35 saved evaluations and 28 saved evidence-quality results** from the scratch restore without mismatch. The scratch database and backup were removed. This confirms local data and calculation recovery, but does not establish a production RPO, RTO, off-host backup process, or recurring restore drill.

A later backup after migration 017 restored successfully. Source and restore matched at **2 tenants, 39 evaluations, 1,300 audit events, 1 review conflict, and 17 migrations**. The non-owner role replayed **all 39 saved evaluations and 32 saved evidence-quality results** without mismatch. The scratch database and backup were removed.

The latest local backup after migration 018 restored successfully. Source and restore matched at **2 tenants, 41 evaluations, 1,386 audit events, 2 review conflicts, 2 review messages, and 18 migrations**. The non-owner role replayed **all 41 saved evaluations and 34 saved evidence-quality results** without mismatch. The scratch database and backup were removed.
